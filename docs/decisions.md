### D-01. 백엔드는 Hono(TypeScript)를 유지한다

- **이유:** 이미 Swagger UI(`/api/swagger`)와 Scalar(`/api/docs`)가 zod 스키마에서 나온다. 프론트와 백엔드가 `packages/contracts`의 같은 스키마를 import하므로 요청 검증, API 문서, 프론트 타입이 한 곳에서 나온다. 언어가 TypeScript 하나라 3명이 서로의 코드를 읽을 수 있다.
- **대안:** FastAPI. Swagger는 기본 제공이지만 Python과 TS 두 언어가 생기고, 프론트 타입을 OpenAPI에서 따로 생성해야 하며, 스캐폴드·CI·배포를 다시 만들어야 한다.
- **다시 볼 조건:** 백엔드를 Python 라이브러리 없이는 만들 수 없는 기능이 생길 때.

### D-02. API와 DB는 EC2 한 대에서 docker compose로 돌린다

- **이유:** 로컬(`infra/compose.yaml`)과 같은 모양이라 이해하기 쉽다. 카카오 로그인과 웹 푸시에 필요한 외부 통신이 추가 비용 없이 된다. 프리 티어 크기(t3.micro) 한 대로 dev와 prod를 함께 돌릴 수 있다.
- **대안:** Lambda + RDS. RDS에 비공개로 붙으려면 Lambda가 VPC 안에 있어야 하고, 그러면 외부 통신에 NAT가 필요해 월 수십 달러가 든다. RDS를 공개로 열면 보안이 약해진다.
- **다시 볼 조건:** 파일럿 이후 실제 사용자가 늘어 가용성(서버 한 대가 멈춰도 계속 동작)이 필요할 때.

### D-03. 웹은 Amplify 앱 두 개, `/api`는 같은 출처 프록시

- **이유:** PR마다 미리 보기 주소가 자동으로 생겨 팀원이 서로의 화면을 바로 본다. 웹과 API가 같은 출처라 로그인 쿠키가 iOS Safari에서 제3자 쿠키로 막히지 않고 CORS가 필요 없다. Amplify의 재작성 규칙은 앱 단위라서 dev와 prod를 앱 두 개로 나눈다.
- **대안:** S3 + CloudFront. 비용은 더 적지만 PR 미리 보기를 직접 만들어야 한다.
- **다시 볼 조건:** 도메인을 확보해 웹과 API를 한 CloudFront 아래로 합칠 때.

### D-04. 사람은 Identity Center, 배포는 GitHub OIDC

- **이유:** 오래 가는 액세스 키가 어디에도 생기지 않는다. 팀원은 SSO로 짧은 자격증명을 받고, GitHub Actions는 이 저장소의 `main`·`release`에서만 역할을 받는다. 팀원 권한은 보기와 접속으로 제한하고 인프라 변경은 관리자만 한다.
- **대안:** IAM 사용자 3명 + 액세스 키. 키가 유출되면 계정 전체가 위험해진다. Identity Center를 쓸 수 없으면 콘솔 비밀번호 + MFA + `aws login`으로 대신한다([aws-setup.md](aws-setup.md) 3-B).

### D-05. DB 도구는 Drizzle ORM + drizzle-kit

- **이유:** 스키마를 TypeScript로 쓰고, SQL 마이그레이션 파일을 만들어 PR에서 검토할 수 있다. 런타임이 가볍다. 규칙은 [database.md](database.md).
- **대안:** Prisma(엔진이 무겁고 배포 이미지가 커짐), Kysely(쿼리는 좋지만 마이그레이션을 따로 골라야 함).

### D-06. react-router + TanStack Query

- **이유:** 화면이 많고(LF-01~LF-20), 로딩·오류·재시도 상태를 화면마다 같은 방식으로 다뤄야 한다. 규칙은 [frontend.md](frontend.md).

### D-07. 애니메이션은 SEED 토큰과 CSS

- **이유:** SEED 컴포넌트가 시트·다이얼로그 움직임을 이미 갖고 있고, 시간·곡선 토큰(`--seed-duration-*`, `--seed-timing-function-*`)이 있다. 라이브러리를 추가하면 번들이 커지고 사람마다 다른 움직임이 생긴다. 규칙은 [interaction.md](interaction.md).
- **다시 볼 조건:** 끌어서 닫기처럼 CSS로 어려운 제스처가 필요할 때.

### D-08. 안내는 제목·본문·사진만

- **이유:** 집주인이 붙여넣은 카톡 문구를 그대로 보여줘야 하고, 입력하지 않은 요일표 같은 구조가 조회 화면에 자동으로 나타나면 안 된다. 상세·첫날 카드·미리 보기가 같은 값을 쓴다. 근거는 [lofi/screens.md](../lofi/screens.md) 데이터 귀속.

### D-09. 팁·메모 작성자는 내부 저장, 다른 거주자에게 비공개

- **이유:** 본인 글 수정·삭제와 신고 처리를 하려면 작성자를 알아야 한다. 다른 거주자에게는 보이지 않는 것만 약속한다. 근거는 [lofi/screens.md](../lofi/screens.md) 작성자 정책.

### D-10. 웹 기본 스타일은 lofi를 따른다

- **이유:** 검토와 발표에 쓴 lofi 화면, 함이 우표의 남색과 같은 인상을 유지한다. 화면을 lofi PNG와 바로 비교할 수 있다.
- **대안:** 스캐폴드의 `#4255c7` 파랑과 시스템 글꼴. lofi와 색이 달라 화면마다 다시 맞춰야 한다.

### D-11. API 문서는 prod에서 기본으로 끈다

- **이유:** Swagger UI·Scalar는 외부 CDN 스크립트를 앱과 같은 출처에서 불러온다. 세션 쿠키가 있는 출처에서 외부 스크립트를 실행하지 않도록 prod 기본값을 끄고, dev는 SSM `/wolgyeham/dev/API_DOCS=true`로 켠다. 로컬은 `NODE_ENV`가 production이 아니라 그대로 켜진다.

### D-12. 공개된 안내의 수정본은 별도 테이블

- **이유:** 수정본을 저장해도 공개 내용과 화면의 ‘수정’ 날짜(`guides.updated_at`)가 바뀌면 안 된다. 43 공개 전 확인에서 ‘수정 공개’할 때 수정본을 공개 내용으로 옮기고, 같은 트랜잭션에서 메모를 `applied`로 바꾼다. 편집을 취소하면 수정본만 지운다.
- **대안:** `guides`에 `draft_*` 컬럼. 행 하나로 끝나지만 수정본 저장이 공개 행을 건드린다.

### D-13. 재확인은 읽을 때 계산한다

- **이유:** 파일럿 규모에서 스케줄러를 따로 두지 않는다. 연결(또는 마지막 확인)에서 `RECONFIRM_INTERVAL_DAYS`(기본 365, lofi 40·45의 “1년에 한 번”)가 지나면 재확인 요청, 그 뒤 14일 무응답이면 `reconfirm_needed`로 본다. `/me`, 권한 확인, 공지 알림 대상이 같은 계산 함수(`lib/reconfirm.ts`)를 쓴다. DB `status`에는 쓰지 않는다.
- **다시 볼 조건:** 재확인 요청을 알림으로 보내야 할 때(그때는 예약 작업이 필요).

### D-14. 이사해도 푸시 구독 행은 남긴다

- **이유:** 구독은 브라우저 단위이고, 같은 계정이 다른 건물로 옮겨 가면 그대로 다시 쓸 수 있다. 알림 대상은 발송 시점의 active 연결로 정하므로 inactive가 되면 자동으로 빠진다. 푸시 서비스가 404·410을 돌려준 구독만 지운다.

### D-15. 수정 메모는 그 건물 거주자와 집주인이 읽는다

- **이유:** lofi 12의 “이 건물 거주자와 집주인이 볼 수 있어요”를 따른다. 쓰기는 active 거주자만, reconfirm_needed는 읽기만 한다. 누가 썼는지는 집주인을 포함해 누구에게도 보이지 않고, 본인에게만 `mine`으로 표시한다.

### D-16. OIDC 신뢰 정책은 불변 식별자 형식을 포함한다

- **이유:** 이 저장소는 GitHub OIDC `use_immutable_subject`를 써서 토큰 `sub`에 조직·저장소 ID가 붙는다(`repo:2026-KW-HACKATHON@329474081/24_3355@1373145913:ref:refs/heads/main`). 이름만 쓰는 형식만 허용했던 신뢰 정책 때문에 2026-09-27 main 병합 뒤 API 자동 배포가 실패했다. `infra/aws/github-oidc-trust.json`에 두 형식을 모두 두고, 관리자가 `aws iam update-assume-role-policy`로 반영한다([aws-setup.md](aws-setup.md) 8).

### D-17. 가입코드 재입력은 재확인이다

- **이유:** 재확인 요청을 놓친 거주자가 현관 QR에서 가입코드를 다시 넣는 것은 ‘아직 여기 산다’는 행동이다. 같은 건물·현재 코드로 연결을 다시 시도하면 `alreadyConnected`로 끝내지 않고 active로 돌리고 확인 시각을 갱신한다. 이사 처리(inactive)된 연결은 해당하지 않는다.

### D-18. 건물을 옮기면 알림을 다시 묻는다

- **이유:** 알림 선택은 연결 완료와 분리한다([lofi/screens.md](../lofi/screens.md) §6). A 건물에서 켠 알림이 B 건물 공지로 조용히 이어지지 않도록, 다른 건물로 연결을 바꾸면 그 사용자의 구독을 지우고 17 알림 선택을 다시 보여준다. 로그아웃할 때도 웹이 그 브라우저의 구독을 먼저 지운다(공용 기기).
- **보완(웹):** ‘켜짐’은 서버 저장을 확인한 구독(`wh.pushSaved`: endpoint·계정)과 지금 브라우저 구독이 모두 맞을 때만 보인다. 서버 저장이 실패하면 브라우저 구독도 끊는다. 내 정보에서는 기록이 없거나 같은 계정의 구독만 다시 저장하고, 다른 계정의 구독은 옮기지 않는다. 건물을 옮기면 브라우저 구독도 끊는다.

### D-19. 개발 도구는 켤 때만

- **이유:** react-grab 막대가 390px 화면에서 하단 주요 버튼을 가려 로컬 시연 중 ‘미리 보기’·‘안내 공개하기’를 누를 수 없었다(QA). 필요한 사람만 `apps/web/.env`에 `VITE_ENABLE_REACT_DEVTOOLS=1`을 넣어 켠다.

### D-20. 제보 반복 제한은 Postgres에

- **이유:** 파일럿 규모에서 Redis를 따로 두지 않는다. 회원은 계정, 비회원은 IP(HMAC) 키로 같은 건물에 정규화한 같은 문구를 10분 안에 다시 보내면 429 `REPORT_TOO_FREQUENT`, 한 시간 10건을 넘으면 429 `RATE_LIMITED`다. (건물, 키) advisory lock으로 동시 요청도 하나만 받는다.
- **알려진 한계:** 통신사 NAT처럼 IP를 나눠 쓰는 비회원은 제한을 함께 받는다. 파일럿에서 문제가 되면 수치를 조정한다.

### D-21. 제보자 구분은 세 가지

- **이유:** lofi는 집주인에게 ‘비회원’·‘거주자’ 정도만 보인다고 한다. 로그인했지만 이 건물 거주자가 아닌 사람을 ‘비회원’으로 보이면 사실과 다르고, 답을 받는 경로(확인 링크 vs 내 정보)도 다르다. 보낸 시점 기준 `resident`·`member`·`guest`로 나누고 이름·계정은 보이지 않는다. ‘처리가 어려움’의 한 줄 설명은 lofi 35를 따라 선택이다.

### D-22. 팁 신고는 운영자가 가린다

- **이유:** 작은 건물에서 신고 수로 자동 가림을 하면 한두 명이 남의 팁을 지울 수 있다. 운영자가 `db:moderate`로 목록을 보고 가리거나 복원한다(웹 화면 LF-19는 권한 모델을 정한 뒤). 가린 팁은 작성자의 내 팁에만 ‘가려짐’으로 보이고, 본인 팁은 신고할 수 없다.

### D-23. 원본 확인 헤더가 있을 때만 X-Forwarded-For를 믿는다

- **이유:** 가입코드 잠금과 비회원 제보 제한은 클라이언트 주소로 센다. EC2 보안 그룹은 AWS 전체가 공유하는 CloudFront 대역을 허용하므로, 누구나 자기 CloudFront 배포로 우리 API에 붙어 `X-Forwarded-For`를 꾸밀 수 있다(보안 리뷰에서 재현). 우리 API CloudFront만 비밀 헤더 `X-Origin-Verify`를 붙이고, API는 이 헤더가 맞을 때만 XFF를 믿는다. dev에서 잰 체인은 Amplify 경유가 `[사용자, Amplify CloudFront, Amplify 프록시(서울 EC2 대역)]`, 직접 접속이 `[사용자]`였다. 그래서 끝에서 두 번째가 CloudFront이고 마지막이 서울 EC2 대역이면 끝에서 세 번째를, 아니면 마지막 값을 쓴다. 헤더가 없으면 접속 주소를 쓴다(한도를 나눠 쓰게 되지만 우회는 막힘).
- **남은 틈:** 서울 EC2에서 보내는 공격자는 Amplify 모양을 꾸며 요청마다 키를 고를 수 있다. 이때는 로그인 전 가입코드 확인의 건물 전체 상한(10분 30번)과 비회원 제보의 건물 전체 상한(시간당 30건)이 막는다. 코드 공간이 커서 이 상한 안에서 가입코드를 맞힐 수 없다.
- **반영 순서:** 관리자가 `infra/aws/add-origin-verify.sh`로 CloudFront에 헤더를 붙인 뒤 API를 배포한다. 반대 순서여도 장애는 없고, 그사이에는 접속 주소 기준으로 센다.

### D-24. 공지 푸시는 응답 뒤에 보낸다

- **이유:** 집주인의 공지 올리기 요청 안에서 대상 전체에 푸시를 보내면, 느린 푸시 서버 하나로 응답이 CloudFront 30초 제한을 넘어 504가 나고 집주인이 다시 눌러 공지가 중복된다(리뷰에서 재현). 발송 기록(`notice_deliveries`)을 만든 뒤 응답하고, 발송은 동시 10개 이하로 백그라운드에서 한다. 사용자당 구독은 5개까지, 404·410은 즉시, 그 밖의 실패는 3번 연속이면 구독을 지운다. 화면 문구는 그대로 ‘발송을 시도했어요’다.

### D-25. 웹의 함이 이미지는 압축 사본

- **이유:** 원본 PNG(540~860KB)를 104~150px로 보여주면 현관 QR 첫 화면에서 수백 KB를 더 받는다. 원본은 `design/characters/hami/images/`에 그대로 두고, `apps/web/src/assets/hami/`에는 표시 크기의 약 2배(화면 360px, 스플래시 640px, 미니 120px)로 줄인 뒤 pngquant로 압축한 사본만 둔다(한 장 6~69KB). 줄일 때 흰색·연회색·남색 바탕에서 원본과 비교해 헤일로·잘림이 없는지 확인한다. 새 포즈는 design에서 먼저 확정한다(AGENTS.md).

### D-26. 웹 푸시 요청은 직접 보낸다

- **이유:** `web-push`의 `sendNotification`은 레거시 `url.parse`로 연결할 호스트를 정해, 우리 허용 검사(WHATWG URL)와 다른 호스트로 연결될 수 있었다(`https://attacker.example;.push.apple.com/…`, 보안 리뷰에서 재현). 또 시간 제한이 유휴 기준이고 응답을 끝까지 모은다. 그래서 `generateRequestDetails`로 암호화·VAPID 헤더만 만들고, 요청은 허용 검사와 같은 호스트의 443으로 직접 보낸다. 요청마다 새 Agent, 10초 전체 제한, 응답 64KB 상한을 둔다.
- **다시 볼 조건:** `web-push`가 WHATWG URL과 전체 시간 제한을 지원할 때.

### D-27. 3D는 CSS·SVG 가벼운 판

- **이유:** 3D는 보조 요소이고 현관 QR 첫 화면의 용량과 속도가 더 중요하다. three.js 같은 렌더러는 수백 KB를 더한다. lofi의 등각 자리표시를 SVG로 그리고, 첫 화면이 그려진 뒤 한 번만 나타나는 효과(층이 쌓이는 정도)를 둔다. 동작 줄이기·크게 보기·불러오는 중·실패에서는 정적 그림이다. 자동 회전, 끝없는 반복, 드래그 회전, 스크롤 가로채기는 없다(D-07, interaction.md §7).
- **다시 볼 조건:** 건물마다 실제 모양을 보여줘야 하는 요구가 생길 때.

### D-28. 약관·개인정보 처리방침 초안

- **이유:** 로그인 전 동의가 형식만 있으면 파일럿을 열 수 없다. 실제 수집 항목(카카오 회원번호, 건물 연결, 알림 주소, 제보·팁·메모 내용과 작성자 계정, 비회원 조회 토큰의 해시)과 보관 기간(세션 최대 90일, 비회원 제보 링크 30일 등)을 코드 기준으로 적은 초안을 `/terms`·`/privacy`에 싣고 ‘초안 · 법률 검토 전’을 표시한다. 로그인할 때 동의한 판과 시각을 `users`에 남겨, 판이 바뀌면 다시 동의를 받을 수 있게 한다.
- **남은 일:** 팀과 법률 검토 뒤 확정한다. 이 초안은 법률 자문이 아니다.
- **판 처리:** 로그인 시작(`consent=<판>`)이나 시연 로그인으로 받은 동의는 서명한 state 쿠키로만 믿는다. 지금 판이 아니면 로그인은 되고 동의는 기록하지 않는다. 판이 바뀌면 웹이 다시 묻고 `POST /api/me/terms-consent`로 기록한다(재로그인 없이). 기존 세션은 막지 않는다.

### D-29. 시연 시작은 `/demo`에서만

- **이유:** 시연 모드(29)는 실제 서비스 첫 화면과 주소·데이터를 분리한다(lofi 화면 규칙). `/demo`는 `DEMO_MODE=true`에서만 열리고, 역할 전환은 시연 로그인, ‘처음 상태로’는 시연 건물만 되돌리는 DEMO_MODE 전용 API다. 누구나 부를 수 있으므로 시연 건물 밖의 데이터는 건드리지 않고 반복 호출을 제한한다. prod는 `DEMO_MODE=false`라 경로가 없다.
- **구현:** `GET /api/dev/demo`(시연 건물·계정·가입코드·비회원 시연 제보 링크, 5초 캐시), `POST /api/dev/reset`(발표용 햇살빌라·새봄하우스만. e2e 건물은 CLI `--reset-demo`로만. 같은 사람 30초에 1번·시간당 10번, 모든 사람 합쳐 30초에 1번·시간당 20번).
- **알려진 한계:** 여러 사람이 시간당 20번을 다 쓰면 한 시간 동안 초기화가 막힌다. 본선 시연 전에는 관리자가 SSM 세션에서 `seed.mjs --reset-demo`로 되돌린다([deploy.md](deploy.md)). 가입코드를 보여주는 것은 시연 데이터이고 DEMO_MODE에서만 열리므로 받아들인다.

### D-30. 시연 데이터 함수는 `db/demo.ts`

- **이유:** `/api/dev/reset`이 CLI와 같은 되돌리기를 써야 한다. 서버 번들이 `seed.ts`를 가져가면 `import.meta.main`이 참이 되어 서버 시작 때 시드가 돌 수 있어서, 시드·되돌리기 함수는 `db/demo.ts`에 두고 `seed.ts`는 인자만 읽는 CLI로 남긴다(esbuild 결과에서 `server.mjs`에 main 블록이 없는 것을 확인).
- **함께 정한 것:** 23 건물 확인을 도입하면서 이미 관리자가 있던 건물은 첫 관리자가 생긴 시각으로 확인 처리했다(마이그레이션 0009 백필). 건물 이름 규칙(1~40자, 제어·방향 문자 불가)은 앱에서만 검증하고 DB CHECK는 두지 않는다(팀이 직접 넣은 행과 충돌 방지).

### D-31. CloudFront → EC2 구간 암호화 (검토 중)

- **문제:** 브라우저 → CloudFront는 HTTPS지만 CloudFront → EC2(8081·8082)는 `OriginProtocolPolicy: http-only`라 세션 쿠키, 제보·팁 본문, `X-Origin-Verify` 값이 인터넷 구간을 평문으로 지난다(마지막 코드 리뷰). 파일럿을 실제 사용자에게 열기 전에 막아야 한다.
- **선택지:**
  1. **원본용 도메인 + 인증서:** 팀 도메인(예: `wolgye.kr`)의 하위 이름을 EC2 고정 IP에 연결하고, EC2에 리버스 프록시(Caddy 등)로 Let's Encrypt 인증서를 붙인 뒤 CloudFront를 `https-only`로 바꾼다. 비용이 거의 없고 지금 구조를 유지한다. 도메인이 필요하다.
  2. **CloudFront VPC origin:** EC2를 사설 서브넷으로 옮겨 CloudFront만 AWS 내부망으로 닿게 한다. 공개 포트가 없어지지만 서브넷 이전과 바깥으로 나가는 통신(ECR·SSM·푸시)을 위한 NAT 비용이 생긴다.
  3. **ALB + ACM:** 가장 표준적이지만 월 비용이 늘고 예산(D-02)에 맞지 않는다.
- **결정 (2026-10-01):** 1번안을 도메인 없이 한다(팀이 도메인을 사지 않기로 함). CloudFront는 IP를 원본으로 받지 않으므로, 원본 이름은 탄력적 IP로 만든 `dev.<a-b-c-d>.sslip.io`, `prod.<a-b-c-d>.sslip.io`(`ORIGIN_DOMAIN`)를 쓴다. EC2의 caddy(`caddy:2-alpine`, 64MB)가 Let's Encrypt 인증서를 HTTP-01로 받고, 실패하면 ZeroSSL로 받는다. caddy는 환경별 `X-Origin-Verify`가 다르면 403이고, 맞으면 CloudFront가 만든 `X-Forwarded-For`를 그대로 API에 넘긴다(D-23 규칙 변경 없음). API 포트는 127.0.0.1에만 연다. 보안 그룹은 CloudFront 목록에서 443(관리형 목록이 규칙 55개로 세어져 규칙 하나만 둠), 전체에서 80(인증서 확인·HTTPS 안내만)이다. 지금 환경은 `infra/aws/switch-origin-tls.sh`의 prepare → 배포 → switch → cleanup으로 옮긴다([aws-setup.md](aws-setup.md) 7-A).
- **받아들인 위험:** 외부 무료 DNS(sslip.io)가 멈추면 원본을 찾지 못하고 인증서를 갱신하지 못한다. sslip.io는 공개 접미사 목록에 없어 Let's Encrypt 한도를 모든 사용자와 나눠 쓴다(넘으면 ZeroSSL). 80이 전체에 열리고, 인증서 이름이 CT 로그에 공개되어 원본 IP가 드러난다(443은 CloudFront만 받고 헤더가 막음).
- **다시 볼 조건:** 팀 도메인을 확보하면 `ORIGIN_DOMAIN`만 바꾼다(코드 변경 없음, rollback → prepare → 배포 → switch → cleanup).
- **지금 상태:** 관리자 반영(cleanup) 전까지 개인정보 처리방침 초안은 이 구간을 ‘준비 중’으로 적는다. 반영 뒤 문구와 `legal.test.tsx`를 함께 고친다.

### D-32. 모든 로그인 입구에서 동의, 폰트 직접 호스팅

- **이유:** 16 화면에서만 동의를 받으면 초대·내 정보·다시 로그인으로 들어온 사람은 약관을 보지 않고 계정이 생긴다. 모든 로그인 버튼이 같은 동의 확인을 거치고 `consent`를 보내며, 이미 현재 판에 동의한 사람은 건너뛴다. 동의 판은 같은 출처에서 시작한 로그인에서만 기록한다(교차 사이트 링크로 동의를 남기지 못하게). Pretendard를 jsDelivr에서 받으면 방문자 IP·브라우저 정보가 처리방침에 없는 제3자로 가므로 앱과 함께 배포한다.

### D-33. prod 웹은 release의 정적 결과물로 배포

- **결정 (2026-10-06):** dev Amplify의 GitHub 연결은 유지하고, prod는 별도 WEB 앱에 GitHub Actions가 `release`의 빌드 결과물을 업로드한다. API 배포 성공 뒤 웹을 올려 계약 버전 순서를 지킨다. 저장소 인증 토큰을 복제하지 않고 기존 OIDC 배포 역할에 prod 앱 release 브랜치만 허용한다.
- **비용 범위:** EC2·DB·CloudFront는 기존 자원을 사용한다. prod 웹은 SSR·WAF 없이 정적 파일만 호스팅하며 추가 사용량은 빌드·저장·전송이다. 무료 한도 적용 여부와 남은 크레딧은 계정 상태에 따라 달라진다.
