### D-01. 백엔드는 Hono(TypeScript)를 유지한다

- **이유:** 이미 Swagger UI(`/api/swagger`)와 Scalar(`/api/docs`)가 zod 스키마에서 나온다. 프론트와 백엔드가 `packages/contracts`의 같은 스키마를 import하므로 요청 검증, API 문서, 프론트 타입이 한 곳에서 나온다. 언어가 TypeScript 하나라 3명이 서로의 코드를 읽을 수 있다.
- **대안:** FastAPI. Swagger는 기본 제공이지만 Python과 TS 두 언어가 생기고, 프론트 타입을 OpenAPI에서 따로 생성해야 하며, 스캐폴드·CI·배포를 다시 만들어야 한다.
- **다시 볼 조건:** 백엔드를 Python 라이브러리 없이는 만들 수 없는 기능이 생길 때.

### D-02. API와 DB는 EC2 한 대에서 docker compose로 돌린다

- **이유:** 로컬(`infra/compose.yaml`)과 같은 모양이라 이해하기 쉽다. 카카오 로그인과 웹 푸시에 필요한 외부 통신이 추가 비용 없이 된다. 프리 티어 크기(t3.micro) 한 대로 dev와 prod를 함께 돌릴 수 있다.
- **대안:** Lambda + RDS. RDS에 비공개로 붙으려면 Lambda가 VPC 안에 있어야 하고, 그러면 외부 통신에 NAT가 필요해 월 수십 달러가 든다. RDS를 공개로 열면 보안이 약해진다.
- **다시 볼 조건:** 파일럿 이후 실제 사용자가 늘어 가용성(서버 한 대가 멈춰도 계속 동작)이 필요할 때.

### D-03. 웹은 Amplify 앱 두 개, `/api`는 같은 출처 프록시

- **이유:** PR마다 미리 보기 주소가 자동으로 생겨 팀원이 서로의 화면을 바로 본다. 웹과 API가 같은 출처라 로그인 쿠키가 iOS Safari에서 제3자 쿠키로 막히지 않고 CORS가 필요 없다. Amplify의 재작성 규칙은 앱 단위라서 dev와 prod를 앱 두 개로 나눈다.
- **대안:** S3 + CloudFront. 비용은 더 적지만 PR 미리 보기를 직접 만들어야 한다.
- **다시 볼 조건:** 도메인을 확보해 웹과 API를 한 CloudFront 아래로 합칠 때.

### D-04. 사람은 Identity Center, 배포는 GitHub OIDC

- **이유:** 오래 가는 액세스 키가 어디에도 생기지 않는다. 팀원은 SSO로 짧은 자격증명을 받고, GitHub Actions는 이 저장소의 `main`·`release`에서만 역할을 받는다. 팀원 권한은 보기와 접속으로 제한하고 인프라 변경은 관리자만 한다.
- **대안:** IAM 사용자 3명 + 액세스 키. 키가 유출되면 계정 전체가 위험해진다. Identity Center를 쓸 수 없으면 콘솔 비밀번호 + MFA + `aws login`으로 대신한다([aws-setup.md](aws-setup.md) 3-B).

### D-05. DB 도구는 Drizzle ORM + drizzle-kit

- **이유:** 스키마를 TypeScript로 쓰고, SQL 마이그레이션 파일을 만들어 PR에서 검토할 수 있다. 런타임이 가볍다. 규칙은 [database.md](database.md).
- **대안:** Prisma(엔진이 무겁고 배포 이미지가 커짐), Kysely(쿼리는 좋지만 마이그레이션을 따로 골라야 함).

### D-06. react-router + TanStack Query

- **이유:** 화면이 많고(LF-01~LF-20), 로딩·오류·재시도 상태를 화면마다 같은 방식으로 다뤄야 한다. 규칙은 [frontend.md](frontend.md).

### D-07. 애니메이션은 SEED 토큰과 CSS

- **이유:** SEED 컴포넌트가 시트·다이얼로그 움직임을 이미 갖고 있고, 시간·곡선 토큰(`--seed-duration-*`, `--seed-timing-function-*`)이 있다. 라이브러리를 추가하면 번들이 커지고 사람마다 다른 움직임이 생긴다. 규칙은 [interaction.md](interaction.md).
- **다시 볼 조건:** 끌어서 닫기처럼 CSS로 어려운 제스처가 필요할 때.

### D-08. 안내는 제목·본문·사진만

- **이유:** 집주인이 붙여넣은 카톡 문구를 그대로 보여줘야 하고, 입력하지 않은 요일표 같은 구조가 조회 화면에 자동으로 나타나면 안 된다. 상세·첫날 카드·미리 보기가 같은 값을 쓴다. 근거는 [lofi/screens.md](../lofi/screens.md) 데이터 귀속.

### D-09. 팁·메모 작성자는 내부 저장, 다른 거주자에게 비공개

- **이유:** 본인 글 수정·삭제와 신고 처리를 하려면 작성자를 알아야 한다. 다른 거주자에게는 보이지 않는 것만 약속한다. 근거는 [lofi/screens.md](../lofi/screens.md) 작성자 정책.

### D-10. 집주인 알림은 문자, 전화번호는 채널일 뿐

- **이유:** 소규모 임대 건물 집주인은 서비스를 배우거나 앱을 깔 동기가 약하다. 브라우저 웹 푸시는 집주인에게 특히 약하다(iPhone은 홈 화면 추가가 먼저, 카카오톡 안 브라우저는 알림 불가). 평소 쓰는 문자로 받으면 앱을 열지 않아도 제보가 도달한다. 이전 계획인 "파일럿에서는 팀이 카톡으로 대신 전한다"는 사람 손이 들어가서 실제 운영으로 이어지지 않는다.
- **권한과 분리:** 관리 권한은 초대 + 카카오 로그인으로만 생긴다(README POL-002). 번호는 이미 권한이 있는 집주인이 직접 등록하는 알림 주소이고, 번호를 아는 것으로 권한이 생기지 않는다. 번호 등록·변경·삭제와 관리자 추가는 문자로 하지 않는다.
- **대안:** 알림톡을 기본 채널로 쓰기 — 답장을 받을 수 없어 이 흐름이 성립하지 않는다. 도착 알림에만 쓰는 추가 채널로는 남겨 둔다(D-15). 전화번호 로그인 — 카카오 로그인과 초대 구조를 다시 만들어야 하고, 번호가 신원이 되면 번호 도용의 피해 범위가 커진다.
- **개인정보:** 번호는 새로 생기는 개인정보다. 발송은 대행 사업자를 거치므로 위탁에 해당한다. 등록 화면에 수집 목적과 보관 기간을 적고, 거주자에게 보이지 않으며 로그에 원문을 남기지 않는다. 근거는 README POL-013.
- **다시 볼 조건:** 집주인이 실제로 앱 알림을 쓰게 되거나, 문자 비용이 감당하기 어려워질 때.

### D-11. 문자 답장 원문을 그대로 공지 본문으로 쓴다

- **이유:** 이 흐름의 목적은 날짜·비용·책임에 대한 오해를 줄이는 것이다. 요약하거나 다시 쓰면 집주인이 말하지 않은 내용이 공지에 생긴다. 원문 그대로면 게시된 문장의 책임이 집주인에게 남고, 집주인은 자기가 보낸 문자와 같은 글을 확인만 하면 된다. D-08(안내는 입력값 그대로)과 같은 원칙이다.
- **LLM을 쓰지 않는 이유:** 요약 모델은 "내일", "곧" 같은 표현을 날짜로 바꾸려 한다. 그게 정확히 이 기능이 막으려던 오해다. 대신 답장을 받은 시각을 함께 저장·표시해서 상대 표현의 기준을 남긴다. AI는 FR-022(한 문장 다듬기)에만 쓰고 공지 경로에는 두지 않는다.
- **오게시 방지:** 게시는 내용 답장과 확인 답장 두 번을 거친다. 대기 질문은 1회용이고 24시간 뒤 만료된다. 게시 직후 되돌리는 방법을 같은 문자로 알린다. 근거는 README POL-014.
- **제보 원문과의 구분:** 초안이 될 수 있는 것은 집주인이 쓴 문장뿐이다. 거주자 제보 원문은 집주인에게만 전달하고 공지에 옮기지 않는다(POL-010).

### D-12. 공지 제목과 적용 기간은 선택

- **이유(기간):** "엘리베이터 점검 3/4~3/5"처럼 기간이 있는 공지와 "현관 비밀번호를 바꿨습니다"처럼 기간이 없는 공지가 섞인다. 기간을 필수로 두면 집주인이 아무 날짜나 넣게 되고, 시스템이 추정해 채우면 D-11의 원칙을 깬다. 문자 답장은 특히 기간을 적기 어렵다.
- **이유(제목):** 문자 답장에는 제목이 없다. 한 통에 제목과 본문을 나눠 쓰라고 요구할 수 없고, 시스템이 제목을 지어내면 집주인이 쓰지 않은 문장이 되어 D-11을 깬다. 제보 종류나 제보 원문을 제목으로 돌려쓰는 것도 POL-010에 걸린다.
- **동작:** 기간이 있으면 끝난 뒤 공개 화면에서 내린다. 없으면 집주인이 직접 내릴 때까지 `published`로 두고 목록에서는 올린 날짜를 기간 자리에 표시한다. 제목이 없으면 목록과 상세에서 본문 첫 줄을 제목 자리에 보여준다. 본문을 잘라 보여주는 것이므로 따로 저장하지 않는다.
- **영향:** `notices.title`·`starts_at`·`ends_at`을 nullable로 바꾸고 기존 기간 CHECK는 둘 다 있을 때만 적용한다. `notices.status`에 `draft`가 생긴다.

### D-13. 수신 문자는 채널 인터페이스 뒤, 시뮬레이터로 먼저

- **이유:** 국내에서 답장을 받으려면 대행 사업자에 양방향 SMS를 따로 신청하거나 050 안심번호를 쓴다. 둘 다 계약과 심사가 필요해서 해커톤 일정 안에 끝난다고 보장할 수 없다. 계약이 늦으면 기능 전체가 막힌다.
- **자르는 방법:** 상태 기계(대기 질문 → 답장 해석 → 처리 → 초안 → 확인 → 게시)와 답장 해석은 채널과 분리한다. 발송·수신은 인터페이스로 두고 `DEMO_MODE`에서 `/api/dev/sms` 시뮬레이터 구현을 붙인다. 개발·CI·시연은 실제 회선 없이 끝까지 돌아간다. 실제 회선이 생기면 구현만 갈아 끼운다.
- **화면과 문자는 같은 로직:** 처리·게시는 관리 화면과 문자가 같은 서비스 함수를 부른다. 문자 쪽은 입구일 뿐이어서, 회선이 없어도 화면으로 같은 일을 할 수 있다.
- **병행:** 발신번호 사전등록과 050 안심번호 확보는 개발과 나란히 진행한다. 결과가 개발 일정을 막지 않는다.

### D-14. 거주자 화면의 기본 모양은 문자

- **이유:** 주 사용자에 60세 이상 거주자가 들어간다. 이들에게 새 앱의 사용법을 가르칠 기회는 없다. 현관 QR을 찍고 처음 들어온 사람이 설명 없이 읽고 보낼 수 있어야 한다. 문자는 이미 매일 쓰는 화면이라 배울 것이 없다. 세부 주제 04(배리어프리)에 대한 답을 기능이 아니라 화면 모양으로도 내는 것이다.
- **무엇을 정했나:** 목록은 보낸 사람·첫 줄·날짜 한 줄, 상세는 보낸 사람·받은 시각·본문 말풍선, 내가 보낸 것은 오른쪽·상대 답은 왼쪽, 쓰기는 입력칸 하나와 보내기 하나. 본문 17px 이상, 주요 버튼 48×48 이상, 한 화면에 할 일 하나. 기준은 [lofi/screens.md](../lofi/screens.md) ‘화면의 기본 모양은 문자’, 정책은 README POL-015.
- **대안:** 큰 글씨 토글과 튜토리얼만 두기. 글자만 커져도 처음 보는 배치는 여전히 낯설다. 크게 보기(FR-025)는 그대로 두고 기본 위의 한 단으로 남긴다.
- **대화로 오해되지 않게:** 모양만 문자이고 실시간 대화가 아니다. 제보 한 건이 한 묶음이고 거주자는 그 안에서만 쓴다. 집주인의 답은 처리 상태와 한 줄까지다. 읽음·입력 중 표시를 만들지 않고, 다른 거주자의 말은 어떤 화면에도 넣지 않는다(POL-003). 말풍선이 모여도 단톡방이 되지 않는다.
- **범위:** 담기는 값과 권한은 그대로다. 모양이 바뀌는 화면은 screens.md ‘문자형으로 다시 그릴 화면’ 표에 적었고, 나머지는 글자·터치 크기만 맞춘다.
- **다시 볼 조건:** 실제 기기에서 60세 이상 사용자가 말풍선을 대화창으로 받아들여 답장을 기대하는 일이 확인될 때.

### D-15. 카카오 알림톡은 도착 알림 전용 추가 채널

- **이유:** 집주인이 문자보다 카카오톡을 더 자주 본다. 도착을 알리는 데는 알림톡이 문자보다 잘 닿는다.
- **제약:** 알림톡으로는 답장을 받을 수 없고, 본문은 사전 심사받은 틀 안에서 변수만 바뀐다. 사업자 등록과 카카오 채널, 템플릿 심사가 필요하다. 그래서 알림톡을 신원이나 답장 경로로 쓸 수 없다.
- **어떻게 쓰나:** 도착 알림과 확인 링크까지만 알림톡으로 보낸다. 처리와 게시는 문자 답장이나 확인 링크로 한다. 집주인이 쓴 문장을 그대로 되읽어 주는 확인 문자(D-11)는 틀에 맞지 않으므로 문자로만 보낸다. 알림톡 발송이 실패하면 같은 내용을 문자로 다시 보낸다.
- **문자를 기본으로 두는 이유:** 알림톡만 쓰면 D-11의 흐름(답장 원문 → 초안 → 확인 → 게시)이 성립하지 않는다. 그래서 D-10의 기본 채널은 문자로 두고, 알림톡은 켜고 끌 수 있는 선택으로 둔다.
- **자르는 방법:** D-13과 같다. 발송은 채널 인터페이스 뒤에 두고 `sms`·`alimtalk`을 값으로 구분한다. 심사가 끝나지 않아도 문자만으로 개발·시연이 끝난다.

### D-16. 글 교정 스킬은 저장소 안에 둔다

- **이유:** 이 저장소는 코드보다 읽히는 문서가 많다. 서비스 제안서(README), `docs/`, `lofi/screens.md`, 이 결정 기록이 모두 심사위원과 팀원이 읽는 글이다. AI가 쓴 티가 나는 문장은 읽는 쪽이 바로 알아챈다. 교정 기준을 각자 계정에 깔아 두면 사람마다 결과가 달라진다. `.claude/skills/humanizer/`에 두면 저장소를 받은 사람은 따로 설치하지 않고 `/humanizer`로 같은 기준을 쓴다.
- **무엇을 정했나:** `blader/humanizer` v4.0.0(MIT)을 `.claude/skills/humanizer/SKILL.md`로 복사하고 `LICENSE`를 같이 둔다. 26개 패턴 중 이 저장소에서 자주 걸리는 것은 "A가 아니라 B" 대비, 같은 말을 되풀이하는 마무리 문장, 문장 전체에 거는 굵은 글씨, 문서 자체를 설명하는 문장("아래 표에서 보듯")이다.
- **대안:** 각자 플러그인으로 설치하기. 버전이 갈리고, 새로 들어온 사람은 받는 방법을 따로 알아야 한다.
- **범위:** 산문만 대상이다. 코드, 표, 숫자, 링크, 파일 경로는 그대로 둔다. em dash를 모두 없애는 규칙(§8)은 스킬 자체가 기준 글의 사용 빈도를 따르라고 정해 두었으므로 이 저장소 문서에 일괄 적용하지 않는다.
- **개인 설정은 올리지 않는다:** `.claude/settings.local.json`은 사람마다 다른 허용목록이 쌓이는 파일이라 `.gitignore`에 넣었다. 저장소에 올라가는 것은 `SKILL.md`와 `LICENSE` 두 개다.
- **다시 볼 조건:** 상위 레포가 규칙을 크게 바꿀 때. 또는 한국어 문장에서 뜻이 달라지는 교정이 나올 때.
