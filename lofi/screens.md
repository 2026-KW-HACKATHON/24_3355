# 화면과 흐름

상태: lofi 46장 + 집주인 문자 채널 + 문자형 화면 기준 반영(2026-09-27). 문자형 화면은 아래 ‘화면의 기본 모양은 문자’ 기준만 확정이고, lofi 46장은 아직 이전 모양입니다. 확정된 라우트 목록이나 Manyfast 동기화 결과가 아닙니다. 화면 흐름과 카드별 조건은 [board.html](board.html)이 기준이고, 이 문서는 흐름·화면 대응, 개발 계약 초안, 남은 상태를 정리합니다. 문자 흐름은 lofi 46장 중 32(집주인 잠금화면 문자) 한 장만 있고, 나머지는 이 문서와 [../README.md](../README.md) §10.3에 글로 있습니다. 바뀐 흐름을 눌러 보려면 [proto.html](proto.html)을 브라우저로 엽니다(제보 → 집주인 문자 답장 → 공지 게시, 11단계).

- **제품 한 문장:** 건물은 기억하고, 사람은 잠시 연결됩니다.
- **HMW:** 어떻게 하면 사람을 위한 또 하나의 방을 만드는 대신, 건물 자체를 지속되는 생활정보 단위로 만들 수 있을까요? (발표 자료와 같은 문장)
- **약속하는 것:** 정보 원본은 월계함 하나. 거주자는 알림을 켰으면 알림으로, 켜지 않았으면 같은 링크로 받고, 집주인은 평소 쓰던 문자로 받습니다. 연결률이 오를수록 반복 전달까지 줄어듭니다.
- **이번 목표:** 모든 기능 화면이 있는 것이 아니라, 처음 보는 집주인도 시작할 수 있고 누구든 중간에 나갔다 돌아와도 하던 일을 이어갈 수 있는 것. 집주인은 앱을 열지 않아도 제보 하나를 끝까지 처리할 수 있는 것. 거주자는 새 앱을 배우지 않고 문자 쓰듯 쓸 수 있는 것.

## 화면의 기본 모양은 문자

60세 이상 거주자에게 가르칠 수 있는 새 사용법은 없다고 봅니다. 그래서 새 모양을 만들지 않고 이미 매일 쓰는 문자 화면의 모양을 그대로 씁니다. 근거는 [../README.md](../README.md) POL-015, 세부 주제 04.

| 항목 | 기준 |
|---|---|
| 목록 | 문자 목록처럼 한 줄에 보낸 사람 · 첫 줄 · 날짜. 한 줄에 정보를 두 개 이상 겹치지 않음 |
| 상세 | 받은 문자 한 통처럼 보낸 사람과 받은 시각 + 본문 말풍선. 제목이 없으면 본문 첫 줄이 제목 자리 |
| 내가 보낸 것 | 내 말은 오른쪽, 집주인 답은 왼쪽. 시간순으로 아래로 쌓임 |
| 쓰기 | 입력칸 하나 + 보내기 하나. 자주 쓰는 말은 누르면 입력칸에 그대로 들어가고 고쳐 쓸 수 있음 |
| 글자 | 본문 17px 이상, 최소 15px. 크게 보기는 그 위의 한 단 |
| 터치 | 주요 버튼 48×48 이상. 연달아 붙은 버튼 사이 8px 이상 |
| 한 화면 | 할 일은 하나. 같은 화면에서 두 가지를 동시에 묻지 않음 |
| 말 | 기능 이름이 아니라 하는 일로 적음(‘제보 등록’ 대신 ‘집주인에게 알리기’) |

- 모양만 문자이고 실시간 대화가 아닙니다. 제보 한 건이 한 묶음이고, 거주자는 그 묶음 안에서만 씁니다. 집주인이 답하는 것은 처리 상태와 한 줄까지입니다.
- 말풍선은 시간순 기록이라서 읽는 순서를 설명하지 않아도 됩니다. 대화창처럼 보여도 상대가 지금 보고 있다는 표시(입력 중·읽음)는 넣지 않습니다. 집주인은 문자로 받고 나중에 답합니다.
- 다른 거주자의 말은 어떤 화면에도 나오지 않습니다. 말풍선이 모여도 단톡방이 되지 않습니다.
- 모양이 바뀌어도 데이터·권한·행동은 그대로입니다. 말풍선에 담기는 값은 아래 ‘2. 데이터 귀속’과 같고, 화면 모양 때문에 값이 늘거나 줄지 않습니다.

## 개발 계약 초안

코드를 쓰기 전에 아래를 `packages/contracts`와 API 정책으로 고정합니다. 화면만 보고 구현하면 해석이 갈립니다. 관리 기능은 버튼을 숨기는 것과 별개로 서버 요청마다 관계를 확인합니다.

### 1. 권한

권한은 로그인 여부가 아니라 이 건물과의 관계로 판정합니다.

| 행동 | 공개(비회원·다른 건물) | 연결 거주자 `active` | 재확인 필요 `reconfirm_needed` | 이사한 사람 `inactive` | 집주인 |
|---|---|---|---|---|---|
| 기본 안내·공지 읽기 | O | O | O | O | O |
| 공지 알림 받기 | X | 선택 | 멈춤 | X | — |
| 생활 팁·수정 메모 읽기 | X | O | O | X | O |
| 생활 팁·수정 메모 쓰기 | X (누르면 44) | O | 멈춤 | X | X |
| 본인 팁 고치기·지우기 | — | O | O | 요청 시 운영팀 | — |
| 팁 신고 | X | O | O | X | O |
| 집주인에게 알리기 | O | O | O | O | X |
| 자기 제보 다시 보기 | 같은 브라우저·확인 링크 | 내 목록 | 내 목록 | 내 목록 | — |
| 제보 처리·메모 판단 | X | X | X | X | O |
| 안내 편집·공지 작성·코드 관리 | X | X | X | X | O |
| 문자 답장으로 처리·공지 | X | X | X | X | 등록한 번호에서만 |

집주인 권한은 월계함 팀이 확인한 건물에 한해 초대 링크로 줍니다. 초대를 수락한 카카오 계정에만 `BuildingManager`가 생기고, 로그인했다는 사실만으로는 관리 권한이 없습니다. 소유권 인증 서비스라고 표현하지 않습니다.

전화번호는 알림을 보낼 곳일 뿐이고 신원 확인 수단이 아닙니다. 관리 권한은 초대와 카카오 로그인으로만 생기고, 번호는 이미 권한이 있는 집주인이 직접 등록합니다. 그래서 문자 답장으로 할 수 있는 일은 이미 가진 권한 안에서만, 그리고 답장 하나로 되돌릴 수 없는 일은 하지 않는 범위로 제한합니다. 번호 삭제·변경, 관리자 추가, 안내 삭제는 문자로 하지 않습니다.

### 2. 데이터 귀속

```text
Building            status: preparing → open (첫 안내 공개)
├─ ManagerInvite    팀이 발급하는 집주인 초대
├─ ManagerPhone     집주인 알림 번호 (건물별 1개, 확인 시각, 사용 여부)
├─ Guide            종류 · 제목 · 본문 · 사진, 수정 시점. draft / published
├─ Notice           공지 (제목·적용 기간은 선택, 올린 경로: 화면 | 문자)
├─ Tip              생활 팁 (author_id 내부 저장)
├─ CorrectionMemo   수정 메모 (Guide에 붙음, author_id 내부 저장)
├─ Report           제보 (회원 계정 또는 비회원 조회 토큰)
│  ├─ OutboundMessage 집주인에게 보낸 문자 (받는 번호 · 종류 · 발송 결과)
│  ├─ ManagerPrompt   대기 중인 질문 (대상 · 선택지 · 만료 시각, 1회용)
│  └─ InboundMessage  집주인 답장 (보낸 번호 · 원문 · 해석 결과)
└─ JoinCode         가입코드 (집주인이 다시 볼 수 있게 보관, 변경 이력)

User
├─ BuildingManager  집주인 관계
├─ Occupancy        입주 관계 (Building ↔ User)
├─ PushSubscription 알림 구독 (기기·브라우저별)
└─ ReportAccess     회원의 제보 조회 권한
```

- 호수(Room)는 없습니다. 사람 ↔ 건물 관계만 다룹니다.
- A가 떠나고 B가 들어와도 `building_id`, `guide_id`, `tip_id`는 그대로입니다. 바뀌는 것은 `Occupancy(A) = inactive`, `Occupancy(B) = active`뿐입니다.
- 안내는 집주인이 입력한 제목·본문·사진만 저장합니다. 상세(11), 첫날 카드(36), 미리 보기(43)는 같은 값을 보여주고, 요일표처럼 입력하지 않은 구조를 자동으로 만들지 않습니다. 개수·순서(1/4 등)는 공개된 안내에서 셉니다.
- 공개 화면의 주소는 도로명까지만 보여주고 번지는 빼며, 건물 페이지는 검색엔진에 노출하지 않습니다.
- 공지 본문은 집주인이 입력한 문장 또는 집주인이 보낸 답장 원문 그대로입니다. 요약·재작성하지 않고, 적지 않은 날짜·비용·책임을 채우지 않습니다. 문자로 올린 공지에는 답장을 받은 시각을 함께 저장해서 ‘내일’ 같은 표현의 기준을 남깁니다.
- 알림 번호는 집주인 본인에게만 가운데를 가린 형태로 보여주고 거주자에게는 보이지 않습니다. 문자 기록(보낸 문자·받은 답장)은 집주인의 처리 이력으로만 보여주고, 번호는 같은 방식으로 가립니다. 로그와 오류 보고에는 번호 원문을 남기지 않습니다.

### 3. 상태 전이

```text
Building        preparing → open
Guide           draft → published →(수정 공개) published
ManagerInvite   issued → accepted | expired
Occupancy       none → active → reconfirm_needed →(아직 살아요) active
                active | reconfirm_needed →(이사·다른 건물 전환) inactive
CorrectionMemo  pending → applied | kept
Report          received → acknowledged → completed | unable
Notice          draft → published →(적용 기간 종료) expired
                draft →(나만 보기) discarded
ManagerPhone    none → pending →(확인 문자 수신) verified → disabled
ManagerPrompt   waiting →(답장) answered | (24시간) expired | (다른 답장) superseded
OutboundMessage queued → sent | failed
NoticeDelivery  target → attempted → opened   (셋을 따로 기록)
```

- `Building`은 안내를 하나 공개해야 `open`이 됩니다. `preparing`인 건물의 QR은 14(안내 없음)를 보여주고, 집주인이 다시 들어오면 “안내를 작성 중이에요 · 이어서 쓰기”로 돌아옵니다.
- `Guide`는 43에서 ‘안내 공개하기’를 눌러야 `published`가 됩니다. 쓰는 중인 내용은 `draft`로 따로 저장하고 공개 화면에는 나오지 않습니다.
- `applied`는 Guide 수정 공개와 같은 트랜잭션에서만 바뀝니다. 편집을 취소하거나 저장이 실패하면 메모는 `pending`으로 남습니다. `kept`는 사유를 함께 남깁니다.
- 집주인이 제보를 열기만 해서는 `acknowledged`가 되지 않습니다. 버튼을 눌러야 합니다. 문자를 받은 것도 여는 것과 같아서, 답장이나 확인 버튼이 있어야 `acknowledged`가 됩니다.
- `Notice`는 화면에서 작성하든 문자 답장에서 오든 먼저 `draft`입니다. 게시는 확인 단계를 한 번 더 거칩니다. 적용 기간이 없는 공지는 `expired`로 자동 전이하지 않고, 집주인이 직접 내릴 때까지 `published`로 둡니다.
- `ManagerPrompt`는 1회용입니다. `answered`·`expired`·`superseded`가 된 질문에 온 답장은 뜻을 정하지 않고, 확인 링크로 안내합니다. 만료는 보낸 뒤 24시간입니다.
- 알아볼 수 없는 답장은 상태를 바꾸지 않습니다. 선택지를 다시 보내고, 같은 제보에 대기 질문을 새로 만들지는 않습니다(기존 질문을 유지).
- 알림 문구는 발송 시도 기준으로 씁니다(“알림 대상 3명에게 발송을 시도했어요”). 도착과 열람을 단정하지 않습니다. 문자도 같습니다. `sent`는 대행 사업자가 접수했다는 뜻이고 집주인이 읽었다는 뜻이 아닙니다.
- 재확인 요청 후 14일 무응답이면 `reconfirm_needed`입니다. 이사로 처리하지 않습니다.

### 4. 작성자 정책

다른 거주자에게 작성자를 보이지 않는 것과 시스템이 작성자를 모르는 것은 다릅니다. 월계함은 앞의 것만 약속합니다.

| 정보 | 내부 저장 | 화면 표시 |
|---|---|---|
| 기본 안내·공지·처리 결과 | 집주인 계정 | 집주인 안내로 표시 |
| 생활 팁 | 작성자 계정 | 다른 거주자에게 작성자 없음, 월 단위 날짜. 본인에게만 ‘내 팁’과 고치기·지우기 |
| 수정 메모 | 작성자 계정 | 집주인에게도 ‘작성자 비공개’. 결과는 해당 안내 아래 메모 상태로 |
| 제보 | 회원은 계정, 비회원은 조회 토큰 | 집주인에게 ‘비회원’·‘거주자’ 정도만 |
| 집주인 알림 번호·문자 기록 | 건물별 번호, 보낸 문자와 받은 답장 | 집주인 본인에게만 가운데를 가린 번호. 거주자에게 없음 |

- 화면에는 ‘익명’이라고 쓰지 않고 실제로 보장하는 범위를 씁니다: “다른 거주자에게 작성자가 안 보여요.”
- 작은 건물에서는 내용으로 작성자를 짐작할 수 있어서, 작성 화면에 “특정인을 짐작할 수 있는 내용은 쓰지 말아 주세요”를 둡니다.
- 부적절한 팁은 거주자·집주인이 신고하고 운영팀이 가립니다(LF-19). 이사한 뒤 본인 팁 삭제는 운영팀 요청으로 처리합니다.
- 이사해도 팁은 건물에 남습니다(작성자 표시 없음).

### 6. 알림 환경

집주인과 거주자는 알림 채널이 다릅니다. 집주인은 문자로 받고, 거주자는 웹 푸시와 앱 안 알림으로 받습니다. 집주인이 앱을 열지 않아도 제보를 처리할 수 있어야 해서, 집주인 쪽은 브라우저 알림 권한에 기대지 않습니다.

| 대상 | 채널 | 켜는 방법 | 받지 못할 때 |
|---|---|---|---|
| 집주인 | 문자 (제보 요약 + 답장 안내 + 확인 링크). 기본 채널 | 관리 홈의 ‘이어서 할 것’에서 번호 등록 → 확인 문자 한 통 | 번호를 등록하지 않아도 관리 기능은 그대로 동작하고, 관리 홈의 ‘확인할 것’에서 직접 확인 |
| 집주인 | 카카오 알림톡 (도착 알림 + 확인 링크). 추가 채널 | 같은 번호 등록 화면에서 ‘카카오톡으로도 받기’ 선택 | 알림톡 발송이 실패하면 같은 내용을 문자로 다시 보냄 |
| 거주자 | 웹 푸시 + 앱 안 알림 | 연결 후 알림 선택(17), 환경별 분기는 아래 표 | 알림을 켜지 않아도 같은 링크와 공개 화면에서 확인 |

거주자 알림 선택은 연결 완료와 분리합니다. 알림을 켜지 않아도 연결은 끝난 상태입니다.

| 상태 | 보여줄 것 | 다음 행동 |
|---|---|---|
| 켤 수 있음 (Android Chrome, 홈 화면에 추가한 iPhone) | “새 공지를 알림으로 받을까요?” | 알림 받기 → 브라우저 권한 요청 |
| iPhone Safari, 홈 화면에 추가 전 (17) | “iPhone은 홈 화면에 추가한 뒤 알림을 켤 수 있어요” + 3단계 | 알겠어요. 내 정보에서 다시 보기 |
| 카카오톡 등 앱 안 브라우저 | “카카오톡 안에서는 알림을 켤 수 없어요” | Safari·Chrome으로 열기 |
| 차단됨 | “지금 알림이 꺼져 있어요” | 설정 방법 안내 |
| 지원 안 됨 | “공지는 우리 건물 화면에서 볼 수 있어요” | 공개 안내와 링크 이용 |

- 카카오톡으로 받은 링크(공지·안내·입주 카드·확인 링크)는 카카오톡 안 브라우저로 열립니다. 이 브라우저는 Safari·Chrome과 저장소를 나누지 않아서 알림과 ‘같은 브라우저 재조회’가 이어지지 않습니다. 외부 브라우저로 여는 방법은 실제 기기에서 확인합니다.
- 집주인에게는 위의 브라우저 분기를 보여주지 않습니다. 관리 홈(42·24)에서 알림 번호가 없으면 등록을 먼저 보여주고, 번호를 등록하지 않아도 화면에서 처리할 수 있게 둡니다.
- 집주인 문자는 두 종류입니다. 제보를 알리는 문자(대기 질문 포함)와 공지 초안을 되읽어 주는 확인 문자입니다. 게시 직후에는 되돌리는 방법을 같은 문자로 알립니다.
- 수신 문자는 대행 사업자 계약이 필요합니다. 파일럿 개발과 시연은 시뮬레이터(`/api/dev/sms`)로 하고, 실제 회선은 채널 구현만 갈아 끼웁니다. 상태 기계와 답장 해석은 채널과 분리해서 둡니다.
- 알림톡은 도착을 알리는 데만 씁니다. 알림톡으로는 답장을 받을 수 없어서, 처리와 게시는 문자 답장이나 확인 링크로만 합니다. 알림톡 본문은 사전에 심사받은 틀 안에서 변수만 바뀌므로 공지 초안을 되읽어 주는 확인 문자에는 쓰지 않습니다.
- 알림톡을 켜도 집주인이 하는 일은 같습니다. 알림톡이 먼저 가고, 실패하면 같은 내용을 문자로 다시 보냅니다. 두 채널 모두 같은 발송 기록에 남고 어느 채널로 갔는지 함께 저장합니다.
- 문자 발송은 대행 사업자를 거치므로 개인정보 위탁에 해당합니다. 번호 등록 화면에 수집 목적과 보관 기간을 적습니다.
- 공지를 올린 뒤(37)에는 “알림을 받지 않는 분에게도 같은 링크로”라고 씁니다. 월계함은 어느 세입자가 연결했는지 보여주지 않으므로, 링크를 누구에게 보낼지는 집주인이 기존 연락처로 판단합니다. 카카오톡 공유는 받을 사람을 직접 고르는 기능이며 자동 발송이 아닙니다.

| 이 브라우저에서 다시 보기 | 브라우저에 남긴 조회 권한으로 QR 재진입 시 배너(30). 공개 QR 주소만으로 본인 제보를 식별하지 않음 |
| 다른 브라우저·기기 | 확인 링크(30일). 링크 복사 또는 카카오톡 공유(나와의 채팅). “본인만 보관해 주세요” |
| 로그인 계정 | 내 정보 › 보낸 내용(21). 비회원 때 보낸 제보를 나중에 로그인해도 자동으로 붙이지 않음 |
| 권한과 링크를 모두 잃음 | “이 브라우저에서는 이전에 보낸 내용을 찾을 수 없어요. 보관한 확인 링크를 열어 주세요” |

- 공개 입구라서 반복 접수 제한(같은 브라우저·같은 문구의 짧은 간격 제한)을 둡니다.
- 제보 원문은 집주인에게만 전달하고 공지에 옮겨 쓰지 않습니다. 화면에서 ‘공지로 알리기’를 누르면 빈 공지 작성 화면을 엽니다.
- 공지 초안이 될 수 있는 것은 집주인이 직접 쓴 문장뿐입니다. 문자 답장은 집주인이 쓴 문장이므로 원문 그대로 초안 본문이 됩니다. 1·2·3 단축키로 답하면 정해진 처리 상태 문구가 초안이 됩니다. 어느 쪽이든 요약하거나 다시 쓰지 않고, 적지 않은 날짜·비용·책임을 채우지 않습니다.
- 그래서 게시된 공지의 표현은 집주인이 보낸 문자와 같습니다. ‘내일’처럼 기준이 필요한 표현은 답장을 받은 시각을 함께 보여주고, 시스템이 날짜로 바꾸지 않습니다.
- 문자로 올린 공지에는 제목이 없습니다. 답장에는 제목이 없고, 시스템이 제목을 지어내면 집주인이 하지 않은 말이 생깁니다. 그래서 공지 제목은 선택이고, 없으면 목록과 상세에서 본문 첫 줄을 제목 자리에 보여줍니다. 제보 종류나 제보 원문을 제목으로 쓰지 않습니다.

### 8. 빈 화면과 오류

| 상황 | 보여줄 것 |
|---|---|

| 대기 질문 만료·중복 답장 | “이미 처리했거나 시간이 지난 요청이에요” + 확인 링크 |
| 등록되지 않은 번호에서 온 답장 | 아무 상태도 바꾸지 않고 응답하지 않음. 번호 확인 안내를 보내지 않음 |

### 구현 순서 (세로로 자르기)

1. **A 최소 증명:** 초대 → 건물 확인 → 안내 작성·미리 보기·공개 → 공개 QR → 비회원이 안내 읽기
2. **B 현재 사람:** 가입코드 → 로그인 → `Occupancy active` → 알림 환경 분기 → 공지 → 알림 대상·링크
3. **C 정보 유지:** 연결 필요 안내 → 내용이 달라요 → 집주인 판단 → Guide 갱신
4. **D 교체:** A 이사(`inactive`, 내 정보에서) → 같은 building 데이터 → B 연결
5. **E 제보(재조회·반복 제한 포함)** → **E' 문자 알림과 답장** → **F 생활 팁(본인 글 관리·신고 포함)**

A~D가 되면 CORE가 완성됩니다. 3D, 읽어주기, 한 문장 초안(AI), 다건물 관리, 동 운영자는 그다음입니다.

E'는 이렇게 자릅니다. 처리와 게시 로직은 화면과 문자가 같은 것을 씁니다. 두 입구가 같은 서비스 함수를 부르는지 먼저 정하고, 그다음에 문자 쪽을 붙입니다.

1. 알림 번호 등록·확인 (`ManagerPhone`)
2. 발송 채널 인터페이스 + 시뮬레이터 구현(`/api/dev/sms`) — 실제 회선 없이 끝까지 돌아가야 합니다
3. 제보 접수 시 발송 + 대기 질문 생성 (`OutboundMessage`, `ManagerPrompt`)
4. 답장 수신·해석 → 처리 상태 변경 (`InboundMessage`)
5. 답장 원문 → 공지 `draft` → 확인 문자 → 게시 + 되돌리기 안내

### 끝까지 해보는 테스트

실제 사용자에게 열기 전에 한 번씩 처음부터 끝까지 수행합니다.

| 테스트 | 통과 조건 |
|---|---|
| 새 집주인 시작 | 설명을 듣지 않고 초대 링크에서 안내 하나를 공개한다 |
| 집주인 재방문 | 건물을 다시 만들지 않고 관리 홈에서 안내를 고친다 |
| 미가입 세입자 | 로그인 없이 필요한 안내를 읽는다 |
| 수정 메모 진입 | 연결이 필요하면 연결을 마친 뒤 보던 안내로 돌아와 메모를 남긴다 |
| 알림 거절 | 알림을 켜지 않아도 연결과 안내 이용이 그대로다 |
| 카카오톡 링크 | 카카오톡으로 받은 링크에서 연결하고, 안내에 따라 알림까지 켠다 |
| 비회원 제보 | 접수 후 창을 닫고, 정해진 경로로 자기 제보 상태를 다시 본다 |
| 문자만으로 처리 | 관리 화면을 한 번도 열지 않고, 문자 답장만으로 제보 1건을 처리하고 공지까지 올린다 |
| 답장 게시 원문 확인 | 게시된 공지 본문이 집주인이 보낸 문자와 글자까지 같다 |
| 알림 번호 없음 | 번호를 등록하지 않은 집주인도 관리 홈에서 제보를 확인하고 처리한다 |
| 안내 수정 실패 | 저장이 실패해도 기존 안내와 메모 상태가 바뀌지 않는다 |
| A의 이사와 B의 입주 | A의 멤버 기능은 끝나고, B는 같은 건물의 남은 안내를 읽는다 |

## 화면 규칙

- 현관 QR로 열면 스플래시·소개·역할 선택·가입 없이 공개 건물 화면이 먼저 보입니다. 스플래시는 홈 화면 아이콘으로 열 때만 씁니다.
- 공개 화면에서 먼저 확인할 것은 ‘내가 들어온 건물이 맞다’와 ‘안내가 여기 있다’입니다. 3D와 함이는 보조입니다. 3D는 로딩 중·실패·‘동작 줄이기’·크게 보기에서 빠지거나 정적 그림으로 바뀌고, 페이지 스크롤을 가로채지 않습니다.
- 하단 탭은 거주자 `우리 건물 · 내 정보`(보낸 내용·내가 남긴 팁·이사는 내 정보 안), 집주인 `건물 관리 · 받은 내용 · 설정`입니다. 동네 탭은 본선 이후입니다.
- 가입하지 않은 거주자도 정상 사용자입니다. 연결하는 이유는 ‘안내 보기’가 아니라 ‘새 공지 알림과 멤버 기능’입니다.
- 로그인은 목적지가 아니라 하던 일을 잇는 중간 단계입니다. 연결을 마치면 누르기 전 화면으로 돌아가고, 환영·첫날 안내·알림 허용을 연달아 강제하지 않습니다.
- 가입코드는 집주인·부동산이 전달하는 6자리 영숫자 코드입니다. 통째로 붙여넣을 수 있어야 합니다. 휴대폰 인증번호나 소유권 증명이 아니고, 카카오 로그인도 거주 확인이 아닙니다.
- 이미 로그인한 사용자는 로그인 단계를 건너뜁니다. 다른 건물로 전환할 때는 기존 관계 변경을 확인하고, 새 연결이 실패하면 기존 관계를 유지합니다.
- 집주인에게 알리기는 자주 쓰는 말을 누르고 확인 시트에서 보내기까지 두 번입니다. 비긴급 공용생활 상황만 다루고, 이웃 분쟁 중재·실시간 대화는 하지 않습니다.
- `처리 완료`는 집주인이 표시한 상태입니다. 해결을 서비스가 확인한 것처럼 말하지 않습니다. 제보 원문은 공지나 안내에 자동으로 공개되지 않습니다.
- 문자는 알림을 보내는 길일 뿐이고 관리 권한을 만들지 않습니다. 문자로는 이미 가진 권한 안의 일만 하고, 게시는 내용 답장과 확인 답장 두 번을 거칩니다. 문자만으로 되돌릴 수 없는 일은 시키지 않습니다.
- 공지 제목과 적용 기간은 선택입니다. 기간을 비우면 올린 날짜를 기간 자리에 보여주고 집주인이 직접 내릴 때까지 둡니다. 제목을 비우면 본문 첫 줄을 제목 자리에 보여줍니다. 시스템이 제목·기간·날짜를 추정해 채우지 않습니다.
- 계속 적용되는 규칙 변경은 공지만으로 끝내지 않고 기본 안내를 고칩니다.
- 생활 팁은 쓰지 않아도 정상 사용자이며 이사 과정에 붙이지 않습니다. 빈 상태에서 작성을 재촉하지 않습니다. 예시 팁에는 집주인 규칙(수거 요일)이나 안전 판단(설비 조작)을 넣지 않습니다.
- 집주인에게는 ‘월계함에 연결된 거주자 N명’으로 보여주고 실제 세입자 수와 다를 수 있다고 적습니다.
- 크게 보기는 같은 서비스를 크게 보는 기능입니다. 연결하기·내가 보낸 내용·관리하기 같은 행동을 빼지 않습니다. 주요 버튼 터치 영역은 44×44 이상을 팀 목표로 둡니다.
- 시연 모드(29)는 실제 서비스 첫 화면과 분리된 주소에서만 열고, 시연용 건물 데이터만 씁니다. 역할 선택으로 실제 권한이 생기지 않습니다.
- 함이는 실제 상태를 설명할 때만 나옵니다. 확인함·처리 완료·처리가 어려움 같은 결과와 집주인 업무 화면에는 나오지 않습니다.
- 콘텐츠 신고 처리는 운영자 업무입니다. 집주인의 안내 수정 검토와 구분합니다.
