# 화면과 흐름

상태: lofi 46장 반영(2026-09-27). 확정된 라우트 목록이나 Manyfast 동기화 결과가 아닙니다. 화면 흐름과 카드별 조건은 [board.html](board.html)이 기준이고, 이 문서는 흐름·화면 대응, 개발 계약 초안, 남은 상태를 정리합니다.

- **제품 한 문장:** 건물은 기억하고, 사람은 잠시 연결됩니다.
- **HMW:** 어떻게 하면 사람을 위한 또 하나의 방을 만드는 대신, 건물 자체를 지속되는 생활정보 단위로 만들 수 있을까요? (발표 자료와 같은 문장)
- **약속하는 것:** 정보 원본은 월계함 하나. 알림을 켠 사람은 알림으로, 알림을 받지 않는 사람은 같은 링크로 받습니다. 연결률이 오를수록 반복 전달까지 줄어듭니다.
- **이번 목표:** 모든 기능 화면이 있는 것이 아니라, 처음 보는 집주인도 시작할 수 있고 누구든 중간에 나갔다 돌아와도 하던 일을 이어갈 수 있는 것.

## 개발 계약 초안

코드를 쓰기 전에 아래를 `packages/contracts`와 API 정책으로 고정합니다. 화면만 보고 구현하면 해석이 갈립니다. 관리 기능은 버튼을 숨기는 것과 별개로 서버 요청마다 관계를 확인합니다.

### 1. 권한

권한은 로그인 여부가 아니라 이 건물과의 관계로 판정합니다.

| 행동 | 공개(비회원·다른 건물) | 연결 거주자 `active` | 재확인 필요 `reconfirm_needed` | 이사한 사람 `inactive` | 집주인 |
|---|---|---|---|---|---|
| 기본 안내·공지 읽기 | O | O | O | O | O |
| 공지 알림 받기 | X | 선택 | 멈춤 | X | — |
| 생활 팁·수정 메모 읽기 | X | O | O | X | O |
| 생활 팁·수정 메모 쓰기 | X (누르면 44) | O | 멈춤 | X | X |
| 본인 팁 고치기·지우기 | — | O | O | 요청 시 운영팀 | — |
| 팁 신고 | X | O | O | X | O |
| 집주인에게 알리기 | O | O | O | O | X |
| 자기 제보 다시 보기 | 같은 브라우저·확인 링크 | 내 목록 | 내 목록 | 내 목록 | — |
| 제보 처리·메모 판단 | X | X | X | X | O |
| 안내 편집·공지 작성·코드 관리 | X | X | X | X | O |

집주인 권한은 월계함 팀이 확인한 건물에 한해 초대 링크로 줍니다. 초대를 수락한 카카오 계정에만 `BuildingManager`가 생기고, 로그인했다는 사실만으로는 관리 권한이 없습니다. 소유권 인증 서비스라고 표현하지 않습니다.

### 2. 데이터 귀속

```text
Building            status: preparing → open (첫 안내 공개)
├─ ManagerInvite    팀이 발급하는 집주인 초대
├─ Guide            종류 · 제목 · 본문 · 사진, 수정 시점. draft / published
├─ Notice           공지 (게시 기간)
├─ Tip              생활 팁 (author_id 내부 저장)
├─ CorrectionMemo   수정 메모 (Guide에 붙음, author_id 내부 저장)
├─ Report           제보 (회원 계정 또는 비회원 조회 토큰)
└─ JoinCode         가입코드 (집주인이 다시 볼 수 있게 보관, 변경 이력)

User
├─ BuildingManager  집주인 관계
├─ Occupancy        입주 관계 (Building ↔ User)
├─ PushSubscription 알림 구독 (기기·브라우저별)
└─ ReportAccess     회원의 제보 조회 권한
```

- 호수(Room)는 없습니다. 사람 ↔ 건물 관계만 다룹니다.
- A가 떠나고 B가 들어와도 `building_id`, `guide_id`, `tip_id`는 그대로입니다. 바뀌는 것은 `Occupancy(A) = inactive`, `Occupancy(B) = active`뿐입니다.
- 안내는 집주인이 입력한 제목·본문·사진만 저장합니다. 상세(11), 첫날 카드(36), 미리 보기(43)는 같은 값을 보여주고, 요일표처럼 입력하지 않은 구조를 자동으로 만들지 않습니다. 개수·순서(1/4 등)는 공개된 안내에서 셉니다.
- 공개 화면의 주소는 도로명까지만 보여주고 번지는 빼며, 건물 페이지는 검색엔진에 노출하지 않습니다.

### 3. 상태 전이

```text
Building        preparing → open
Guide           draft → published →(수정 공개) published
ManagerInvite   issued → accepted | expired
Occupancy       none → active → reconfirm_needed →(아직 살아요) active
                active | reconfirm_needed →(이사·다른 건물 전환) inactive
CorrectionMemo  pending → applied | kept
Report          received → acknowledged → completed | unable
Notice          published → expired
NoticeDelivery  target → attempted → opened   (셋을 따로 기록)
```

- `Building`은 안내를 하나 공개해야 `open`이 됩니다. `preparing`인 건물의 QR은 14(안내 없음)를 보여주고, 집주인이 다시 들어오면 “안내를 작성 중이에요 · 이어서 쓰기”로 돌아옵니다.
- `Guide`는 43에서 ‘안내 공개하기’를 눌러야 `published`가 됩니다. 쓰는 중인 내용은 `draft`로 따로 저장하고 공개 화면에는 나오지 않습니다.
- `applied`는 Guide 수정 공개와 같은 트랜잭션에서만 바뀝니다. 편집을 취소하거나 저장이 실패하면 메모는 `pending`으로 남습니다. `kept`는 사유를 함께 남깁니다.
- 집주인이 제보를 열기만 해서는 `acknowledged`가 되지 않습니다. 버튼을 눌러야 합니다.
- 알림 문구는 발송 시도 기준으로 씁니다(“알림 대상 3명에게 발송을 시도했어요”). 도착과 열람을 단정하지 않습니다.
- 재확인 요청 후 14일 무응답이면 `reconfirm_needed`입니다. 이사로 처리하지 않습니다.

### 4. 작성자 정책

다른 거주자에게 작성자를 보이지 않는 것과 시스템이 작성자를 모르는 것은 다릅니다. 월계함은 앞의 것만 약속합니다.

| 정보 | 내부 저장 | 화면 표시 |
|---|---|---|
| 기본 안내·공지·처리 결과 | 집주인 계정 | 집주인 안내로 표시 |
| 생활 팁 | 작성자 계정 | 다른 거주자에게 작성자 없음, 월 단위 날짜. 본인에게만 ‘내 팁’과 고치기·지우기 |
| 수정 메모 | 작성자 계정 | 집주인에게도 ‘작성자 비공개’. 결과는 해당 안내 아래 메모 상태로 |
| 제보 | 회원은 계정, 비회원은 조회 토큰 | 집주인에게 ‘비회원’·‘거주자’ 정도만 |

- 화면에는 ‘익명’이라고 쓰지 않고 실제로 보장하는 범위를 씁니다: “다른 거주자에게 작성자가 안 보여요.”
- 작은 건물에서는 내용으로 작성자를 짐작할 수 있어서, 작성 화면에 “특정인을 짐작할 수 있는 내용은 쓰지 말아 주세요”를 둡니다.
- 부적절한 팁은 거주자·집주인이 신고하고 운영팀이 가립니다(LF-19). 이사한 뒤 본인 팁 삭제는 운영팀 요청으로 처리합니다.
- 이사해도 팁은 건물에 남습니다(작성자 표시 없음).

| 집주인 알림 | 해당 제보·메모 상세(07·25). 관리 권한이 없으면 “이 건물을 관리할 권한이 없어요” |
| 비회원이 메모·팁 쓰기 | 연결 안내(44) → 02 → 16 → 누르기 전의 작성 화면. 내용은 자동으로 보내지 않음 |
| 로그인 만료 | 다시 로그인한 뒤 보려던 화면 |
| 홈 화면 아이콘 | 스플래시(00) 약 1초 → 거주자 홈 |

### 6. 알림 환경

알림 선택은 연결 완료와 분리합니다. 알림을 켜지 않아도 연결은 끝난 상태입니다.

| 상태 | 보여줄 것 | 다음 행동 |
|---|---|---|
| 켤 수 있음 (Android Chrome, 홈 화면에 추가한 iPhone) | “새 공지를 알림으로 받을까요?” | 알림 받기 → 브라우저 권한 요청 |
| iPhone Safari, 홈 화면에 추가 전 (17) | “iPhone은 홈 화면에 추가한 뒤 알림을 켤 수 있어요” + 3단계 | 알겠어요. 내 정보에서 다시 보기 |
| 카카오톡 등 앱 안 브라우저 | “카카오톡 안에서는 알림을 켤 수 없어요” | Safari·Chrome으로 열기 |
| 차단됨 | “지금 알림이 꺼져 있어요” | 설정 방법 안내 |
| 지원 안 됨 | “공지는 우리 건물 화면에서 볼 수 있어요” | 공개 안내와 링크 이용 |

- 카카오톡으로 받은 링크(공지·안내·입주 카드·확인 링크)는 카카오톡 안 브라우저로 열립니다. 이 브라우저는 Safari·Chrome과 저장소를 나누지 않아서 알림과 ‘같은 브라우저 재조회’가 이어지지 않습니다. 외부 브라우저로 여는 방법은 실제 기기에서 확인합니다.
- 집주인도 같은 분기를 거칩니다. 관리 홈(42)에서 알림 설정이 안 됐으면 먼저 보여줍니다.
- 파일럿에서는 집주인 웹 푸시에 기대지 않습니다. 팀이 받은 메모·제보를 보고 집주인에게 카톡으로 전합니다. 상용화 단계에서 알림톡을 검토합니다.
- 공지를 올린 뒤(37)에는 “알림을 받지 않는 분에게도 같은 링크로”라고 씁니다. 월계함은 어느 세입자가 연결했는지 보여주지 않으므로, 링크를 누구에게 보낼지는 집주인이 기존 연락처로 판단합니다. 카카오톡 공유는 받을 사람을 직접 고르는 기능이며 자동 발송이 아닙니다.

### 8. 빈 화면과 오류

| 상황 | 보여줄 것 |
|---|---|
| 불러오는 중 | 로딩 상태 (3D는 정적 그림) |
| 건물은 있지만 공개된 안내 없음 | “아직 등록된 안내가 없어요”(14) |
| 연결 문제로 불러오기 실패 | “불러오지 못했어요” + 다시 시도. 안내 없음으로 표시하지 않음 |
| 건물 주소가 유효하지 않음 | “건물 정보를 찾을 수 없어요”(22) |

| 공지 기간 종료 | “종료된 공지예요” + 기본 안내로 |
| 제보 보관 기간 종료 | “보관 기간이 지나 더 이상 확인할 수 없어요” |

### 구현 순서 (세로로 자르기)

1. **A 최소 증명:** 초대 → 건물 확인 → 안내 작성·미리 보기·공개 → 공개 QR → 비회원이 안내 읽기
2. **B 현재 사람:** 가입코드 → 로그인 → `Occupancy active` → 알림 환경 분기 → 공지 → 알림 대상·링크
3. **C 정보 유지:** 연결 필요 안내 → 내용이 달라요 → 집주인 판단 → Guide 갱신
4. **D 교체:** A 이사(`inactive`, 내 정보에서) → 같은 building 데이터 → B 연결
5. **E 제보(재조회·반복 제한 포함)** → **F 생활 팁(본인 글 관리·신고 포함)**

A~D가 되면 CORE가 완성됩니다. 3D, 읽어주기, 한 문장 초안(AI), 다건물 관리, 동 운영자는 그다음입니다.

### 끝까지 해보는 테스트

실제 사용자에게 열기 전에 한 번씩 처음부터 끝까지 수행합니다.

| 테스트 | 통과 조건 |
|---|---|
| 새 집주인 시작 | 설명을 듣지 않고 초대 링크에서 안내 하나를 공개한다 |
| 집주인 재방문 | 건물을 다시 만들지 않고 관리 홈에서 안내를 고친다 |
| 미가입 세입자 | 로그인 없이 필요한 안내를 읽는다 |
| 수정 메모 진입 | 연결이 필요하면 연결을 마친 뒤 보던 안내로 돌아와 메모를 남긴다 |
| 알림 거절 | 알림을 켜지 않아도 연결과 안내 이용이 그대로다 |
| 카카오톡 링크 | 카카오톡으로 받은 링크에서 연결하고, 안내에 따라 알림까지 켠다 |
| 비회원 제보 | 접수 후 창을 닫고, 정해진 경로로 자기 제보 상태를 다시 본다 |
| 안내 수정 실패 | 저장이 실패해도 기존 안내와 메모 상태가 바뀌지 않는다 |
| A의 이사와 B의 입주 | A의 멤버 기능은 끝나고, B는 같은 건물의 남은 안내를 읽는다 |

## 화면 규칙

- 현관 QR로 열면 스플래시·소개·역할 선택·가입 없이 공개 건물 화면이 먼저 보입니다. 스플래시는 홈 화면 아이콘으로 열 때만 씁니다.
- 공개 화면에서 먼저 확인할 것은 ‘내가 들어온 건물이 맞다’와 ‘안내가 여기 있다’입니다. 3D와 함이는 보조입니다. 3D는 로딩 중·실패·‘동작 줄이기’·크게 보기에서 빠지거나 정적 그림으로 바뀌고, 페이지 스크롤을 가로채지 않습니다.
- 하단 탭은 거주자 `우리 건물 · 내 정보`(보낸 내용·내가 남긴 팁·이사는 내 정보 안), 집주인 `건물 관리 · 받은 내용 · 설정`입니다. 동네 탭은 본선 이후입니다.
- 가입하지 않은 거주자도 정상 사용자입니다. 연결하는 이유는 ‘안내 보기’가 아니라 ‘새 공지 알림과 멤버 기능’입니다.
- 로그인은 목적지가 아니라 하던 일을 잇는 중간 단계입니다. 연결을 마치면 누르기 전 화면으로 돌아가고, 환영·첫날 안내·알림 허용을 연달아 강제하지 않습니다.
- 가입코드는 집주인·부동산이 전달하는 6자리 영숫자 코드입니다. 통째로 붙여넣을 수 있어야 합니다. 휴대폰 인증번호나 소유권 증명이 아니고, 카카오 로그인도 거주 확인이 아닙니다.
- 이미 로그인한 사용자는 로그인 단계를 건너뜁니다. 다른 건물로 전환할 때는 기존 관계 변경을 확인하고, 새 연결이 실패하면 기존 관계를 유지합니다.
- 집주인에게 알리기는 자주 쓰는 말을 누르고 확인 시트에서 보내기까지 두 번입니다. 비긴급 공용생활 상황만 다루고, 이웃 분쟁 중재·실시간 대화는 하지 않습니다.
- `처리 완료`는 집주인이 표시한 상태입니다. 해결을 서비스가 확인한 것처럼 말하지 않습니다. 제보 원문은 공지나 안내에 자동으로 공개되지 않습니다.
- 계속 적용되는 규칙 변경은 공지만으로 끝내지 않고 기본 안내를 고칩니다.
- 생활 팁은 쓰지 않아도 정상 사용자이며 이사 과정에 붙이지 않습니다. 빈 상태에서 작성을 재촉하지 않습니다. 예시 팁에는 집주인 규칙(수거 요일)이나 안전 판단(설비 조작)을 넣지 않습니다.
- 집주인에게는 ‘월계함에 연결된 거주자 N명’으로 보여주고 실제 세입자 수와 다를 수 있다고 적습니다.
- 크게 보기는 같은 서비스를 크게 보는 기능입니다. 연결하기·내가 보낸 내용·관리하기 같은 행동을 빼지 않습니다. 주요 버튼 터치 영역은 44×44 이상을 팀 목표로 둡니다.
- 시연 모드(29)는 실제 서비스 첫 화면과 분리된 주소에서만 열고, 시연용 건물 데이터만 씁니다. 역할 선택으로 실제 권한이 생기지 않습니다.
- 함이는 실제 상태를 설명할 때만 나옵니다. 확인함·처리 완료·처리가 어려움 같은 결과와 집주인 업무 화면에는 나오지 않습니다.
- 콘텐츠 신고 처리는 운영자 업무입니다. 집주인의 안내 수정 검토와 구분합니다.

## 아직 그리지 않은 상태

가입코드 오류와 5회 실패 후 10분 대기, 로그인 취소 후 복귀, 가입 중 코드 변경, 기존 건물 관계 변경 확인, 알림 환경의 나머지 상태(카카오톡 안·차단·지원 안 됨), 집주인 알림 설정, 공개 전 ‘이어서 쓰기’, 관리 권한 없음, 작성 중 닫기, 저장 실패(입력 유지), 중복 전송·반복 제한, 전송 결과 불명확, 확인 링크 만료·잃음, 3D 로딩 실패, 메모 ‘기존 유지’ 사유 입력, 거주자의 메모 결과 보기(안내 아래 확인 전·반영됨·기존 유지), 팁 고치기·지우기·신고, 콘텐츠 신고 가림(LF-19), 공지 만료 링크, 긴 건물 이름·긴 본문, 홈 상단 재확인 배너(시트 40만 있음). 구현하면서 같은 화면의 상태로 추가합니다.
